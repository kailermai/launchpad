# Personal Launcher — Build Plan

## 1. Project Goal

Build a **safe, local-first Windows application/game launcher** that replaces desktop shortcut clutter with a clean, visual library.

The launcher should let you:

- manually add games and applications
- drag-and-drop shortcuts or executables to add them quickly
- automatically prefill the application name and path from the dropped file
- organize apps by **platform** and **category**
- mark favorites
- view recently launched apps
- search and filter the library
- randomly choose a game from a user-selected pool
- save random-picker presets
- export/import launcher configuration backups
- launch configured applications

The launcher should **not** scan the computer automatically and should **never modify, move, rename, delete, uninstall, or alter the files of any configured application**.

---

## Safety Rules

These five rules are what keep the launcher safe for the rest of the PC. Every other section must respect them. Each one is a line or two of code, not a feature.

| # | Rule | Where it is enforced |
|---|------|----------------------|
| 1 | Launch only via `ShellExecuteW` — the same thing Windows does on double-click. Never a shell command, never a concatenated command string. Do **not** include `tauri-plugin-shell` in the project. | the single `launch_application` command |
| 2 | Launch takes an application **ID**, never a path. The Rust side loads the path from the database, so the UI can never say "run this path". | command signature |
| 3 | Allowed launch targets are only `.exe`, `.lnk`, and URIs whose scheme is `steam://` or `https://`. Checked on save, on import, and on launch — not just in the file dialog. | one validation function |
| 4 | The launcher only creates, modifies, or deletes files inside its own `%APPDATA%/PersonalLauncher/` folder. Nothing outside that folder is ever written to. Covers are **copied** in, never moved. | the two functions that touch files (cover copy, database) |
| 5 | Tauri config: `assetProtocol.scope` limited to the launcher's own `assets/` folder, no `fs` plugin (or scoped to the launcher folder only), strict CSP, no network, no updater. | `tauri.conf.json` / capabilities, set once |

Because no delete / move / rename / scan / shell code exists in the project, it cannot run.

Three small notes that follow from the rules:

- The launcher itself never runs elevated (installed per-user, never requests admin). If a game needs UAC, Windows will prompt on its own.
- Reading a dropped `.lnk` for name/target prefill is **read-only** — parse the file (e.g. the `lnk` crate); never call `IShellLink::Resolve` + `Save`, which can rewrite the shortcut.
- If zip backups are ever built (V1.1), reject any zip entry containing `..`, an absolute path, or a drive letter, and extract only into `assets/`.

# 2. Design Principles

## 2.1 Safety First

The launcher should have an intentionally small permission surface.

### Allowed

- Open an explicitly configured executable, shortcut, or supported URI.
- Read launcher-owned configuration and database files.
- Read metadata from a file the user explicitly selects or drops onto the launcher.
- Read a user-selected image used as cover art.
- Check whether a configured launch target still exists.
- Store local launcher metadata.
- Remove an entry from the launcher database.
- Export and import launcher configuration.

### Not Allowed

- Scan drives or folders for installed games.
- Discover applications automatically.
- Delete files.
- Move files.
- Rename files.
- Modify application/game folders.
- Edit save files.
- Uninstall software.
- Modify the Windows Registry.
- Run arbitrary shell commands supplied by the user or generated by AI.
- Recursively inspect folders without an explicit user action.

A key UI rule:

> Use **"Remove from Library"**, never **"Delete Application"**.

Removing an entry must only remove launcher metadata.

# 3. Recommended Technology Stack

## Desktop Framework

**Electron + React + TypeScript** (chosen 2026-09-18; Tauri was the first pick but needs the Rust + MSVC toolchains, which are not installed on this PC)

Why:

- runs on the Node toolchain already installed — nothing else to install system-wide
- frontend development stays familiar and fast
- native file dialogs, drag-and-drop, `.lnk` reading and icon extraction are built in
- does not require a separate backend
- launches explicitly configured files through a narrow, typed preload bridge

How the five Safety Rules map to Electron:

| Rule | Electron mechanism |
|---|---|
| 1 | `.exe` → `child_process.spawn(path, [], { shell: false })`; `.lnk` → `shell.openPath`; links → `shell.openExternal` |
| 2 | Renderer calls `launchApplication(id)`; main process reads the path from the database |
| 3 | `src/main/validate.ts` allowlist, applied on save, import and launch |
| 4 | Only the main process touches disk, under `app.getPath('userData')` = `%APPDATA%\PersonalLauncher\` |
| 5 | `contextIsolation` + `sandbox`, no `nodeIntegration`, strict CSP, navigation blocked, `cover://` protocol scoped to `assets/` |

SQLite is provided by `sql.js` (SQLite compiled to WebAssembly — no native compiler needed); the database file is rewritten atomically after every committed transaction.

## Database

**SQLite**

Store the launcher library locally.

Suggested file:

```text
%APPDATA%/PersonalLauncher/launcher.db
```

## Covers / Artwork

Store user-selected artwork in an app-owned folder:

```text
%APPDATA%/PersonalLauncher/assets/
```

Prefer copying selected artwork into the launcher-owned directory instead of relying on the original image path forever.

## Backups

Export configuration as JSON:

```text
personal-launcher-backup-2026-09-18.json
```

The backup should contain launcher metadata only.

It should never copy or package the actual installed games/applications.

## 9.2 EXE Handling

For:


```text
Executable
```


Name cleanup should be conservative.

## 9.3 Windows Shortcut (.lnk) Handling

If the user drops:

```text
Hades.lnk
```

the launcher should inspect only that explicitly dropped shortcut.

It may extract:

```text
Shortcut display name
Target path
Icon source, if available
```

Two safe implementation options:

### Option A — store the shortcut itself

```text
launch_type = shortcut
launch_target = C:\Users\...\Desktop\Hades.lnk
```

Launching the shortcut lets Windows handle whatever the shortcut points to.

### Option B — resolve the target

Read the shortcut metadata and store:

```text
launch_type = executable
launch_target = resolved target
```

**Option A is simpler and safer for V1.**

It also supports shortcuts that have custom parameters or special launcher behavior.

# 10. Drag-and-Drop Safety Rules

Drag-and-drop must **never** mean:

```text
move file
copy executable
modify shortcut
delete shortcut
```

It only means:

```text
READ USER-SELECTED FILE METADATA
        ↓
CREATE LAUNCHER ENTRY
```

The original file remains untouched.

The application should not recursively inspect the dropped file's containing folder.

# 27. Native Tauri Commands

Keep the native API deliberately tiny.

Possible commands:

```text
launch_application(id)
choose_application_file()
choose_cover_image()
read_dropped_file_metadata(path)
check_application_target(id)
export_backup()
import_backup()
```

`launch_application` and `check_application_target` take an **ID** and look the path up in the database (Safety Rule 2). The only command that accepts a path from the UI is `read_dropped_file_metadata`, and it must refuse anything that is not a regular `.exe` or `.lnk` file.

Avoid commands such as:

```text
delete_file()
move_file()
rename_file()
run_shell()
scan_directory()
scan_drives()
```

Ideally those commands simply do not exist in the backend.

# 28. Launch Logic

Pseudo-flow:

```text
User clicks PLAY
        ↓
UI sends the application id only
        ↓
Rust loads the application record
        ↓
Validate launch_type + extension / URI scheme (Safety Rule 3)
        ↓
If local path:
    check file exists
        ↓
ShellExecuteW(target, working directory = target's own folder)
        ↓
If successful:
    update last_launched_at
```

The working directory is set to the executable's folder so games write their saves/logs where they expect to, not wherever the launcher happens to be running from.

For V1, support:

```text
.exe
.lnk
```

Optional:

```text
steam://...
https://...
```

through explicit URI entries later.

- [ ] The launcher never moves game files.
- [ ] The launcher never modifies the registry.
- [ ] Remove from Library only removes launcher metadata.

## Backup

- [ ] I can export launcher configuration.
- [ ] I can restore launcher configuration.

# 35. Nice-to-Have Features After V1

Only consider these once the basic launcher is already being used.

Possible additions:

- multiple visual themes
- cover aspect-ratio options
- custom accent color
- grid density setting
- pinned collections
- sorting by name / recently launched / date added
- "Surprise Me" shortcut on the home screen
- random picker weights
- global hotkey to open launcher
- fullscreen console-style mode
- controller navigation

Explicitly avoid scope creep into:

- automatic PC scanning
- automatic game-library import
- playtime process monitoring
- game-file management
- mod management
- uninstalling
- auto-updating games

Those features significantly increase complexity and permissions without improving the core use case.

# 36. Final Product Definition

The final V1 launcher should feel like:

> **A safe, polished personal shelf for everything I choose to launch.**

The launcher knows only what you explicitly add.

It can:

```text
remember
organize
search
group
randomly choose
launch
```

It cannot:

```text
scan
move
rename
modify
delete
uninstall
```

That boundary is what keeps the project simple and trustworthy while still making it fun to use.
